# 时间轴拖动方案

## 方案一：高帧实时解码预览

**核心思路**：使用独立的 `MediaMetadataRetriever` 实例，在拖动过程中按需实时解码原始分辨率帧，用 `Image` 覆盖层替代 `PlayerView` 显示，实现清晰流畅的拖拽预览。

### 关键实现要点

- **PlayerViewModel**：管理一个常驻的 `MediaMetadataRetriever` 实例
- **onTimelineDragStart**：初始化 Retriever，暂停播放器，设置拖拽状态
- **onDragPositionChanged**：每次手指位置变化时，以 ~80ms 为间隔节流，在 IO 线程调用 `getFrameAtTime()` 解码当前时间位置的帧
- **onTimelineDragEnd**：释放 Retriever，恢复播放器，隐藏预览图层，执行 `seekTo()` 跳转到最终位置
- **PlayerScreen**：拖拽时隐藏 `PlayerView`，用 `Image` 显示实时解码的 Bitmap；拖拽结束后恢复 `PlayerView`

### 优缺点

| 方面 | 说明 |
|------|------|
| 优点 | 画面清晰（原始分辨率）、帧率流畅（60fps+）、交互接近剪映体验 |
| 缺点 | 代码复杂度高；需要管理 Retriever 生命周期；CPU/解码器占用较高 |
| 适用场景 | 对拖拽预览体验要求高的视频播放器 |

## 方案二：seekTo 节流

**核心思路**：拖拽时 scrollOffset 立刻更新（保证时间轴 UI 流畅），但 `player.seekTo()` 仅以较低频率调用（比如每 100ms 一次）。

### 关键实现要点

- 手指拖动时，**每次**手势回调都立即更新 scrollOffset/currentOffset，保证时间轴光标跟随手指，视觉上无延迟
- 但 `player.seekTo()` 调用加一个时间闸：只在距离上次 seek 超过阈值（如 100ms）时才发起
- 这样在连续快速拖动时，seek 频率从 60~120 次/秒降低到约 10 次/秒，大幅减少 ExoPlayer 的解码压力和中途中断

### 优缺点

| 方面 | 说明 |
|------|------|
| 优点 | 实现简单、改动最小；时间轴滑动始终流畅，无滞后感；降低 ExoPlayer seek 频率，减少解码压力 |
| 缺点 | 松手前视频画面更新频率较低（~10fps），帧跳动明显；无法与剪映式实时帧预览相比 |
| 适用场景 | 快速实现、对帧预览要求不高的场景 |
